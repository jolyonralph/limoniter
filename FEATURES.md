# What Limoniter can do

Limoniter is a text and hex editor for Windows, also released for Linux (as an AppImage and a .deb) and for Macs (Apple Silicon and Intel). Alongside everyday editing it knows the character sets, file formats and media of older computers: it opens 8-bit and 16-bit text byte for byte, previews retro screens, pictures and BASIC programs, and browses disk images, tapes and archives from classic machines without changing them. It compares files and whole folders, merges three versions of a file, and can be what Git uses to show differences and resolve conflicts.

Every command is in the menus, arranged by what it is for. Press **F1** to find any command by describing what it does. On a Mac, shortcuts use Cmd where this list says Ctrl, Option and an arrow moves by a word, Cmd+[ and Cmd+] go back and forward, and files open from Finder by double-clicking or Open With.

## A full IDE for a folder of code

Open a folder (File, Open folder) and Limoniter works across all of it, as VS Code does: an Explorer with Git's status, Go to file and Go to symbol, a Search panel that shows each replacement before it's made, language servers that it offers and installs for you, debugging for Python, C, C++ and Rust, files side by side, breadcrumbs and sticky scroll, and terminals in tabs. The same folder keeps its tasks, tests, Git and notes.

- **Open folder** (File), as VS Code opens one: the folder is the project, with an **Explorer** in the Project panel that shows it as it is on the disk, a folder read as it's opened and read again when it changes, so files made, renamed or deleted elsewhere show by themselves. Folders first; what Git leaves out (.gitignore in each folder, and .git/info/exclude) fainter; .git and its kind not shown. The file being edited is found in the tree. New files and folders and renaming are typed in the tree; right-click for Find in this folder, Open a terminal here, Show in the file manager, Copy path and Copy relative path, the comparisons, and Move to the Recycle Bin (asked first). Open files follow a renamed file or folder. Its project file (open tabs, tasks, notes, saved comparisons) is kept beside Limoniter's settings, so nothing is written into the folder, unless the folder has a `NAME.limproj` of its own at its top.
- **Go to file** (Ctrl+E): a few letters of a file's name, and its folders', find it among every file in the folder (made in the background, leaving out what Git leaves out, and kept up to date), letters together and at the starts of words counting most, as VS Code's quick open does; the Explorer's own box does the same. Find in Files' Project files are the folder's too. Checked on Limoniter's own source, over 1,500 files.
- **Go to symbol** (Ctrl+T in the folder, Ctrl+Shift+O in the file): # in the Go to file box finds a function or label, by a few of its letters, in every file of the open folder (found in the background with each language's grammar, only changed files read again), and @ in the file in front, in order down the file; Enter goes to its line.
- **Search panel** (Search, **Ctrl+Shift+F**), as VS Code's: what's typed is searched for in the open folder (or the project, or the file in front's folder and those in it), as it's typed, with match case, whole words and regular expressions, and files to search and to leave out by name (`*.rs;*.s`). What's found is a tree, each file (with its folder and how many) and under it each line with the match marked; a click goes there. With something to put in its place, each match shows struck through with the new text after it (a regular expression's groups put in), so the change is seen before it's made. A file can be put out of the way (×), and Replace all, or the file's own ⇄, asks first and then changes files open here in their tabs (to undo) and the rest on disk, then searches again. Find in files (the old box, Search menu) is still there.
- **The Explorer shows Git's status:** a changed file's name in Git's colours with its letter at the right (M changed, A added, U not tracked yet, D deleted, R renamed, ! in conflict), and a dot on each folder with changes in it. **Drag a file or folder** onto a folder (or a file in one) to move it there; open files follow.
- **Language servers** (Settings, Editing; off until switched on): for C, C++, Rust, Python, JavaScript, TypeScript, Go, Java, Lua, shell scripts and any other language given a server, the server for the file's language (rust-analyzer, clangd, pylsp and the rest, installed separately) is started in its project's folder and gives completion as you type (or Ctrl+Space), hover, Go to definition (F12), Find all uses (Shift+F12), Rename (Ctrl+F12) across files, and problems marked beside their lines and said in the status bar. Settings shows which servers are installed, and which command serves each language can be changed. Also: **Quick fix** (**Ctrl+.**), the server's fixes and refactorings for the cursor's line, an edit made at once or a command whose edits the server sends; **Format document** (**Shift+Alt+F**), and formatting on save (Settings, Language servers); **parameter hints**, the call being typed's signature over the line with the parameter being typed marked; and **inline hints**, the types and parameters' names a server gives, faint at the ends of lines. A server that stops says why in the Output panel. **Offered when they'd help:** a file whose language has a server that's installed while servers are off has it offered (Use it, Not now, Never for that language); one whose server isn't installed, or wouldn't start, has it installed in a terminal (rustup, pip or pipx, npm, go, winget, apt or brew, as the server is installed), and started once it's there.
- **Debugging** (Tools, Run, **Ctrl+F5**) through the Debug Adapter Protocol, as VS Code debugs: **Python** with debugpy, and **C, C++ and Rust** with gdb's own adapter (gdb 14 and later) or lldb-dap. Breakpoints are set beside the line numbers, as in assembler source, and the line it's stopped on is marked and brought into view (another file opened if need be). The Debug panel has Carry on (F5), Step over (F10), Step in (F11), Step out (Shift+F11), Pause and Stop (Shift+F5); the call stack, each frame a click away with its own variables; the variables, opened a level at a time; and a console with what the program prints, and expressions worked out in the frame. A script is run as it is; for a compiled program, which program (the debug build Cargo makes, guessed), its arguments and folder are asked once. Checked with a real debugpy.
- **Another file beside this one** (Window, Split, **Ctrl+\**; or **Ctrl+Enter** in Go to file): two tabs side by side, as VS Code's editor groups. The one in front has a line along its top; clicking in the other brings it to the front, on its own side, and a tab chosen above takes the front one's place. The divider drags. (One above the other and Side by side split a single file in two, as before.)
- **Breadcrumbs** (View, Show) above the text: the file's folders from the open folder, its name, and the function or label the cursor is in. Each is a menu: a folder's files (and its folders, as menus) to open, the file's neighbours, or the file's functions and labels to go to. **Sticky scroll** keeps the function or label scrolled past at the top of the text, a click away. Both come from the file's outline, found in the background a moment after typing stops.
- **Peek definition** (**Alt+F12**): where the word at the cursor is defined, a few lines of it with the line itself marked, in a window over the text; Open it goes there. It asks the language server, Limoniter's assembler, or else goes by name, through the file's outline and the open folder's symbols, which **Go to definition** (F12) now does too for files neither follows.
- **Terminal** (View, **Ctrl+`**): your shell (PowerShell on Windows, your own elsewhere) in a panel under the text, in the open folder or the folder of the file in front, on a real pseudo-terminal (ConPTY on Windows), so colours, the cursor keys and full-screen programs work as in any terminal. **Several terminals**, each a tab with its folder's name (+ for another); Ctrl+` hides the panel and shows it again with the shells still running. Restart gives a fresh shell; closing one ends it, and the next comes forward.
- **Tasks** (Tools, Tasks): build, run and test commands, found from a project's own files (Cargo, a Makefile's targets, package.json's scripts, Go, pytest, CMake) or kept with a Limoniter project (Edit the project's tasks), run in the project's folder with everything open saved first. **Ctrl+Shift+B** runs the build task and **Ctrl+Shift+T** the test task. Where compilers and tools say problems are (gcc, clang, rustc, Go, Python tracebacks, MSVC, the assemblers) is a click away in the Output panel, and marked by its line in the files open.
- **Test results**: a test task's output (cargo test, pytest, go test) is read test by test into a panel, failures first, each a click away from where it failed, with **Run again** and **Run only this** for a failing test.
- **.editorconfig**: the files in a file's folder and those above (up to one with `root = true`) set its indentation (indent_style, indent_size, tab_width) while it's in front, the line endings of a new file, and on saving trim_trailing_whitespace and insert_final_newline; their globs as the specification has them.

- **The Explorer** sorts by name, type, size or date, with folders first or mixed in, and can show each file's size and when it was changed (the ⇅ button at its top). Each file has a badge of its kind, as on the tabs and in Go to file.
- **Go to file** shows the file chosen as the choice moves through the list: its first lines, or those around a symbol, with the symbol's line marked.
- **TODO notes** (View, Panels): TODO, FIXME, BUG, HACK and XXX in comments, in the file in front or across the whole project, each a click from its line.
- **A live server** (Tools, Run, Serve this folder in a browser): the folder is served on this computer only (from port 5500), the page in front opens in the browser, and every page reloads when a file's saved. Choose it again to stop.
- **External formatters**: where no language server formats the file, Format document (**Shift+Alt+F**) and formatting on save use a formatter installed for the language: Prettier, Ruff, Black, isort, clang-format, shfmt, gofmt, rustfmt, StyLua, Taplo, xmllint or jq. **Format, Formatters** chooses each language's, among those installed.
- **Microcontrollers**: a folder with platformio.ini has PlatformIO's build, upload, test and serial monitor tasks; with AVR or PIC code open and a .hex built, Tools, Tasks, Run has a task that flashes it with avrdude or MPLAB IPE's ipecmd, with the programmer, chip and port chosen in Tools, Tasks, Microcontroller flashing.
- **Time spent** (Tools, Time spent; off until switched on there): the time spent working, by project, language, file and day, for today, the week, 30 days or all; kept in a file beside the settings on this computer, and sent nowhere. A pause of over two minutes isn't counted.
## Editing

- Tabs for open files; **Ctrl+Tab** goes back through files in the order they were used.
- Split a file into two panes (one above the other, or side by side), or open a second tab on it.
- Column mode (**Alt+C**), or **Alt**+drag for a block selection; typing then works on every selected line.
- Columns: insert or fill, cut, delete, justify left/centre/right, number them, and add up the numbers.
- Lines: move up and down, join, sort A to Z or Z to A, indent, outdent, trim leading or trailing spaces.
- Change case: UPPER CASE, lower case, Sentence case, Title Case.
- Text objects: select, replace or delete inside or around quotes, brackets, tags, a word, a line or a paragraph.
- Select every copy of the selection, or to the matching bracket.
- Insert the date, time, file name or path, a GUID, a page break, a colour, a byte by its value, or another file.
- Snippets (**Ctrl+J**) with `$CURSOR`, `$SELECTION`, `$DATE`, `$TIME` and `$FILE` filled in.
- **Surround with** (Edit): puts the selection between brackets, quotes or a tag of your own, or into a snippet that has `$SELECTION`, and leaves it selected inside; with nothing selected, the cursor goes between the pair.
- Swap with clipboard (**Ctrl+Shift+V**) puts the selection on the clipboard and the clipboard in its place.
- Undo as a tree: undoing and then typing keeps the undone branch; the Edit history shows every state.
- Edit history can be kept with the file between sessions.
- History of this part (**Ctrl+Alt+H**): the changes to just the selected lines or function, each of which can be taken back on its own.
- Narrow to the selection (**Ctrl+Shift+N**): every command then works on just those lines.
- Folding, hiding chosen lines, and showing only the lines that contain the selection.
- Colour tags (**Ctrl+Shift+1** to **6**) mark sections in six colours, shown in the margin and the document map, and kept with the file.
- Bookmarks, and back and forward (**Alt+Left**, **Alt+Right**) through where the cursor has been, across files. **Search, Bookmarks** goes to any of them by its line, and copies, cuts or deletes the bookmarked lines (or deletes every other line), swaps bookmarked and not, or clears them all.
- Show line numbers, ruler, document map, changed lines, spaces and tabs, line endings, control characters by name, rainbow brackets and the cursor's line and column.
- **Column markers** (View, Show): lines down the text after chosen columns, up to eight (80 to begin with; 7 and 72 for COBOL, 72 for commit messages), set in Settings.
- **Line spacing** (Settings, Appearance): rows from as close as the font sets them to twice as far apart.
- Spell checking with Windows' own dictionary, in Windows' language; **F7** goes to the next mistake with suggestions.

- **Indentation guides** (View): a faint line down each level of indentation, at the file's own indent; coloured by depth if wished (Settings).
- **Problems at the ends of their lines**: each line's problem written faintly after it, in its colour, as well as marked beside it.
- **Colours shown where they're written**: #rrggbb, rgb(), hsl(), and the Amiga's $0RGB on a line with a COLOR register, each underlined in its colour; with the cursor in one, a swatch above it opens a picker, and the colour chosen is written back the same way.
- **Comment kinds in colour**: TODO, FIXME, BUG and HACK, NOTE and REVIEW in comments, and whole comments beginning with ! (a warning) or ? (a question), in colours of their own.
- **Hide comments** (View): comments aren't drawn, the file unchanged.
- **Folds take in their closing bracket**: a folded block shows as { … } on one line.
- **HTML and XML tags**: typing an opening tag's > puts its closing tag after the cursor (not for HTML's empty elements, such as br and img); changing a tag's name changes its partner's with it, one Undo taking back both; and the pair the cursor's in is marked.
- **File paths finished as they're typed**: in a string, an include or an import, the files and folders in the folder written so far, from the file's own folder.
- **Doc comments** (Format, Doc comment for this function): from the signature on the cursor's line, or just below or above it, each parameter and the return listed: a Python docstring, a /** */ block with @param and @return (C, C++, Java, JavaScript, TypeScript, PHP, Kotlin and the like), C#'s XML comments, Rust's and Swift's ///, and Go's comment naming the function.
- **Markdown**: lists carry on as Enter's pressed (bullets, numbers counting on, and task boxes), an empty item ending the list; **Format, Markdown: table of contents** puts in a linked table of contents of the headings between markers, kept up to date each time the file's saved; **Markdown: line up the table** lines up the columns of the table the cursor's in, as its line of dashes aligns them; and markdownlint's usual problems are marked as a language server's are (MD001, MD009, MD010, MD012, MD018, MD022, MD025, MD031).
- **Trim trailing spaces as a file's saved** (Settings), and only on the lines changed since it was opened if wished, so the rest of its history isn't touched; .editorconfig's trim_trailing_whitespace has the last word, and trims the whole file.
## Laying out text and code

- Reindent by brackets; break long lines at a column; join each paragraph into one line.
- **Tabs and spaces** (Format): whether the Tab key types spaces, the tab size, tabs to spaces (everywhere, or only in each line's indent), spaces to tabs in the indent, trimming spaces at either end of lines, and showing spaces and tabs.
- **Convert** (Format): Base64 encode and decode (RFC 4648, in 76-character lines; URL-safe letters and missing padding read too), JSON to XML and XML to JSON (members as elements, `@name` as attributes, `#text` as an element's text, an array as the element repeated; numbers, true, false and empty elements come back as such).
- Paragraphs: reformat to a width and margins, align left, centre, right or justify.
- Lay out code: HTML, XML, JSON, JavaScript, CSS, SQL and C-like code (brace on the same line or its own line).
- Compress HTML, XML, JSON, JavaScript and CSS onto as few lines as possible.
- EDI files: one segment to a line, or all onto one line.
- Comma-separated text to fixed-width columns and back.
- Comment out and uncomment lines in the file's language.
- The formatters only ever change spacing; if anything else would change, the text is left alone.

## Table view

- **View › Table view** (**F6**) shows comma-, tab-, semicolon- or pipe-separated data as rows and columns. A file that looks like such data is offered as a table when it's opened, and .csv and .tsv files can open as tables straight away.
- The text is still the document: changing a cell changes only that field, keeping every other field's quoting and spacing as it was, so one Undo takes it back and saving writes exactly what you'd expect.
- Type or double-click to change a cell; Enter keeps it and moves down, Tab moves across, Esc leaves it as it was.
- Select a block of cells with Shift and the arrow keys, Shift+click or by dragging. Copy puts it on the clipboard as a spreadsheet would, so it pastes into Excel or LibreOffice; a block copied from a spreadsheet pastes in, adding rows past the end, as one step for Undo. Delete empties the block, and one value pasted over it fills every cell.
- The total, average, smallest and largest of the numbers in the selection, or in the cursor's column, are shown above the table.
- Fields in quotes may hold the delimiter, quotes and line breaks (RFC 4180); a quote inside an unquoted field is just a character.
- Click a heading to show the rows in order of that column (numbers as numbers), and type to show only the rows that contain something; neither changes the file. **Sort the file by this column** does, keeping the headings at the top.
- Insert and delete rows and columns. Rows with the wrong number of fields, or a quote that's never closed, are marked.
- The first row can be headings or data; columns can be dragged wider or narrower, or double-clicked to fit. The row numbers, and the first column if asked, stay in view when the table is scrolled sideways. Find moves the table to the row it finds.
- It works on files of any size. Above 64 MB the records are found, rows sorted and filtered, and the figures added up in the background, with the progress shown above the table; inserting or deleting a column and sorting the file rewrite it in the background too, as one step for Undo.
- It isn't a spreadsheet, and cells don't hold formulas.

## Hex editing

- **Ctrl+H** switches any file between text and hex.
- The character pane can show the file's own character set, or EBCDIC.
- Overwrite or insert bytes; insert or delete a number of bytes at the cursor.
- Go to an offset in decimal or hex (`0x...`).
- Search for hex byte sequences as well as text.
- Copy the selected rows as they look on screen.
- **Value inspector** (View, Hex): the bytes at the cursor as every kind of number: 8-, 16-, 32- and 64-bit integers either way round, signed and not; IEEE floats and doubles either way round; IBM hexadecimal floating point (System/360 and ICL 2900), 32- and 64-bit; DEC VAX F, D, G and H floats, words swapped as a VAX keeps them; packed decimal (COBOL COMP-3); and RADIX-50, three characters a word as PDP-11 and VAX names keep them.
- String explorer: lists readable strings in the bytes and how each is stored (length prefix, zero terminator, fixed-width padding, top bit set on the last character, `$` terminator, or line ending); can also find UTF-16 strings.

## Large files

- Files of any size open quickly: those of 64 MB and more are kept on disk and read a part at a time (tested with a 10 GB file).
- Edits are kept in memory beside the untouched parts of the file, and saving copies the untouched parts straight across in the background.
- Hex mode works on files of any size, binary or text: a large binary file opens straight into hex. Typing, inserting, deleting, undo, search and Replace All all work, and the offset column widens past 4 GB.
- Search and Replace All in a huge file run a stretch at a time, with progress shown, so the window stays usable.
- Recovery copies of a huge file hold only the edits, not the whole file.
- Word Count and Save a copy in another encoding go through a huge file in the background.
- The string explorer looks through a huge file a stretch at a time (up to its first 200,000 strings).
- Reindent, converting the encoding or the line endings in place, Filter on selection, hiding lines, Compare, printing and table view all work on a huge file; those that go through the whole file do it in the background, with progress shown, and one Undo takes back a change.
- The new files those commands write are deleted when Limoniter closes; if it stops unexpectedly, they're deleted the next time it starts, unless a recovery copy still needs one.
- Still not available above 64 MB: Fold all, the function list, the assistant, previews, BASIC listings and program saving, and tracing a part's history.

## Character sets and encodings

- 201 single-byte character sets, plus UTF-8, UTF-16 and UTF-32 (both byte orders), UTF-7, and East Asian encodings (Shift-JIS, EUC-JP, ISO-2022-JP, GBK, GB 18030, Big5, EUC-KR).
- Windows and ISO-8859 code pages, KOI8, and 20 DOS code pages (CP437, CP850, CP866 and others).
- 18 classic Macintosh encodings, HP Roman-8, DEC Multinational, NeXTSTEP and Palm OS.
- 22 EBCDIC code pages for IBM mainframes, with and without the euro.
- 8-bit home computers: Commodore PETSCII and screen codes (C64/C128, VIC-20, PET), Atari ATASCII and screen codes, Atari ST, ZX Spectrum, ZX80, ZX81 and QL, BBC Micro and Mode 7, Acorn Atom, RISC OS, Amiga, Amstrad CPC, Amstrad PCW and CP/M Plus (the PCW's text and its screen, with its symbols and graphics), Amstrad NC100, NC150 and NC200, Cambridge Z88, MSX (five regional sets), Apple II, TRS-80, Sharp MZ and X1, Oric, Kaypro, Osborne and more.
- 26 teletext national character sets.
- The 7-bit national versions of ASCII (ISO 646): UK, German, French (1973 and 1982), Italian, Spanish (two), Portuguese (two), Swedish and Finnish (and for names), Norwegian (two), Danish, Swiss, Hungarian, Irish and Icelandic; DEC Special Graphics, the VT100's line drawing; DEC Technical, the VT220's maths symbols, bracket pieces and Greek; and ASCII with the top bit set, as Prime computers kept text, its line feed 0x8A.
- Opening and saving give back the same file byte for byte; bytes with no Unicode equivalent are carried through exactly.
- Each line keeps its own line ending: CRLF, LF, CR, ATASCII (0x9B), EBCDIC NL (0x15), Prime's 0x8D 0x8A, or fixed-width rows with none.
- Change the encoding or line ending from the status bar; reopen with another encoding, convert, or save a copy in another.
- Character table panel: every byte of the current character set with its glyph, name and Unicode value, and a Unicode browser.
- Encoding preview panel: the selected text or the character at the cursor as code points and as the bytes it is stored as.

## Syntax highlighting

- The large set of languages bundled with the two-face collection (C, Rust, Python, HTML, Markdown, SQL and many more).
- 40 grammars written for Limoniter, mostly for older systems:
  - Assemblers: 6502, 65816, 6809, 680x0, 8080, 80x86, Z80, ARM, AVR, PIC, PDP-11, VAX, IBM HLASM.
  - BASICs: Commodore, Sinclair, QBasic, AMOS, Blitz Basic, STOS.
  - Mainframe and business: COBOL, JCL, PL/I, RPG, REXX, MUMPS, xBase.
  - Others: APL, Forth, Logo, Modula-2, Prolog, Smalltalk, PostScript, RTF, Inform 6, ZIL, CONFIG.SYS.
  - Amiga: Amiga E (`.e`: its capitalised keywords, built-in functions and constants, `->` and nested `/* */` comments, and each PROC and method in the outline), AmigaGuide and the Amiga Installer language.
- Choose the language by hand with **Tools, Colour as** (or by clicking the language in the status bar): a box with the 224 languages grouped **by kind** (assembly, BASIC, systems, the web, data, documents, mainframes and the rest), **by machine** (ZX Spectrum, Commodore, BBC Micro, Amiga, Atari, Apple II, Dragon and Vectrex, the PC, microcontrollers, IBM mainframes, Unix, the web and more, a language in every group it belongs to, as 6502 assembly is the C64's, the BBC Micro's, the Atari's and the Apple II's) or **A to Z**. Typing finds one by a few letters of its name, or of a group it's in (`amiga` finds 680x0 assembly, AMOS and AmigaGuide); the arrows and Enter choose. Work it out (saying what it would choose), Plain text and the languages chosen lately are at the top.
- **Your own grammars**: Sublime Text `.sublime-syntax` files put in the grammars folder beside the settings (Settings, Editing, Open the folder) are read when Limoniter starts, and win over the built-in grammar for a file ending both know. Any that can't be read are listed there with the reason.

## Previews

Shown beside the text or filling the window (**View, Preview**). Nothing in a preview runs or fetches anything.

- Markdown, with headings, lists, tables, emphasis, code and links. A link to a file beside the page (with no `..`, no folder from the root and no web address) opens it in Limoniter, and pictures beside it (PNG and SVG) are shown in place; anything else stays as text.
- **Mermaid diagrams** in Markdown, drawn in the preview without Mermaid or any JavaScript: flowcharts (every node shape, labelled and dotted and thick links, subgraphs), sequence diagrams (actors, activations, notes, loop, alt, opt and par frames, autonumber), state diagrams (composite states, choices, forks), class diagrams (members, annotations and every kind of relation with cardinalities), entity-relationship diagrams with crow's feet, pie charts and Gantt charts, laid out in layers to cross as few lines as they can, in the theme's colours. Other kinds are shown as their text. SVG pictures beside a Markdown file are drawn too, and the table of contents' links scroll to their headings.
- **File, Save the preview as PDF**: Markdown, a web page, a converted document or a BASIC listing laid out on A4 pages, numbered, with its headings as bookmarks and its table of contents linked to them, its links, tables, code, pictures and Mermaid diagrams (as lines and words, not pictures). Under the assembler's section:
- **Call graph** (View, Panels): an assembly program's routines and which calls which (CALL, RST, JSR, BSR, LBSR, BL), read from what Limoniter's own assembler made of it as you type, drawn down or across; a click on a routine goes to it. For other code, its language server's call hierarchy for the function at the cursor.
- **Instruction reference** (View, Panels): the instruction the cursor is on, for the Z80, 6502, 6809, 68000, x86 and ARM: each form with its bytes (and its cycles, for the Z80 and 6502), as the assembler makes them, and for the first four what it does, which flags it changes and (6809, 68000) its cycles.

- **AMOS** programs (`.AMOS`, from AMOS 1.0 to AMOS Professional) are listed as AMOS lists them, with AMOS's own spacing and indents, locked procedures unlocked, what saved them, whether they were tested and the memory banks saved with them; and a listing is tokenised back (**Format, Tokenised BASIC, Save as an AMOS program**): every keyword of AMOS Professional and its four standard extensions, each in the form its arguments call for, numbers in AMOS's single or (after Set Double Precision) double precision, and each procedure's distance to its End Proc, so AMOS loads it ready to test and run. Checked on 17 AMOS programs from Aminet, which come back the same apart from what AMOS fills in when it tests a program.
- **STOS** programs (`.BAS` that start Lionpoulos, from the Atari ST) are listed as STOS's LIST shows them, following STOS 2.06's own routines from its released source, with their memory banks; and a listing is tokenised back (**Format, Tokenised BASIC, Save as a STOS program**), keywords found as STOS finds them (even inside a name, as STOS does). Instructions from STOS extensions are kept as `extension_A_3C`, and go back as they were. Checked on 38 STOS programs, which come back byte for byte apart from what STOS fills in as it runs, and against STOS's own text listings saved beside them.
- MSX-BASIC, Atari BASIC, Integer BASIC, and the TRS-80's, ZX81's, SAM's and Oric's BASICs are listed only; protected MBASIC programs are reported, not listed. A damaged program is listed as far as its lines link up, and says where it stops. MBASIC, MSX-BASIC and TRS-80 Model 4 programs, which are saved alike, are told apart by the tokens in them.

## Comparing files and folders

- **Tools › Compare with…** compares the file in front with another open file or one on disk; **Compare files…** asks for two files. They open side by side in a tab of their own.
- Both sides can be edited, with Undo, and saved. A file that's already open is compared as it is in its tab, unsaved edits and all, and edits made in the comparison are made there.
- Changed lines are marked in colour and with a sign beside each line (~ changed, - only on the left, + only on the right), and the words or characters that differ within a line are marked more strongly.
- Previous and Next go from one difference to the next (Search › Next change does too). An arrow between the sides copies a difference across, in one step that Undo takes back.
- Spaces, case and line endings can be ignored. The two sides scroll together.
- **Save as a patch** writes the differences as a unified diff, as patch and git apply read.
- Files that aren't text are compared byte by byte, in hex, with each byte that differs marked. Pictures Limoniter can show are compared as pictures, with a third showing where they differ.
- Files too large to hold in memory are compared in the background and shown read-only.
- **Tools › Compare folders…** compares two folders as a tree, side by side: each entry is the same, different (and which side is newer), only on one side, or a file on one side and a folder on the other, in words as well as colour. Folders open and close, what's the same can be hidden, and double-clicking a pair of files compares them.
- Either side can also be a Git revision (HEAD, a branch, a tag or a commit), a disk image or archive (chosen with Browse), or a folder on an SFTP server you've connected to before, picked from your saved sites.
- Compare by size and time, or by contents. Only some files can be taken (such as `*.rs; *.toml`), others left out, and what `.gitignore` files leave out can be left out too. Comparing runs in the background, with progress, and can be stopped.
- **Copy to the right** and **Copy to the left** copy what's chosen across, into a folder here or on a server. A list of what will happen is shown first; nothing is deleted, and each file replaced is kept in a backup folder first.
- **Sync** brings two sides into step. **Update** copies newer and missing files left to right, right to left, or both ways with the newest winning, and never deletes. **Mirror** makes one side exactly like the other, deleting what the other hasn't got. Either shows a list of every new file, replacement and deletion first, with counts, to untick what you don't want; a mirror that deletes asks again, saying how many. Each file replaced or deleted is kept first in a backup folder named for the time, and a file changed since the comparison is left alone.
- A saved comparison remembers how both sides were after its last sync, so a file changed on both sides since is shown as a conflict and left alone unless you tick it. A file deleted from one side since the last sync isn't copied back unless ticked.
- Files can be synced into a folder on an SFTP server, signing in only with the password kept in the system's credential store or the site's key, and only to a server whose key you've trusted. Disk images, archives and Git revisions are only read; syncing into one says why not.
- **Save this comparison** keeps both sides, how they're compared, the filters, rules, Hide what's the same and the sync's direction by name. With a project open it's kept in the project and listed under **Comparisons** in the Project panel; otherwise beside the settings. **Tools › Saved comparisons…** opens, renames and deletes them.
- **Rules for comparing files** (Settings › Files, or **Rules…** in a comparison for its own) say how files are compared by name: as text leaving out spaces, case, line endings or lines matching a pattern such as a timestamp; byte by byte; as pictures (the same pixels are the same); by size and time only; or always left out. The usual rules leave out `*.o`, `*.obj`, `target/`, `.git/` and the like. They apply when folders are compared and when a pair is opened.
- **Save a report** saves the comparison as an HTML page or plain text, the counts only (for the whole and each folder at the top), or a CSV file for a spreadsheet; **Save as a patch** saves every difference in the text files as one unified diff.
- **Apply a patch** (Tools, or in a folder comparison for either side) checks a unified diff against a folder or one file, showing for each change whether it fits, fits a few lines away, or can't be found. A file any of whose changes can't be found is left as it is; each file written is backed up first, and line endings are kept.
- In the Project panel, a file's menu has **Compare with…** and a folder's has **Compare folders…**; both have **Compare with the last commit**. Saved comparisons are listed under **Comparisons**.

## Remote files

- **File › Open a file from the web (http/https)**: give a web address and the file is fetched and opened as any file is (an image in the browser, text with its encoding found); it has no file of its own until you save it where you choose.
- **File › Open a remote file (SFTP or FTP)** connects to a server, browses its folders and opens a file; **Save to a server** puts any document there.
- **FTP and FTPS** as well as SFTP: ftp:// for plain FTP (an Ultimate 64, an Amiga, a MiSTer), ftpes:// for FTP with TLS asked for, ftps:// for TLS from the start. A certificate no authority has signed, as a home server's usually is, is shown to be trusted the first time, as an SSH server's key is. The password can be kept in the system's credential store.
- **File › Open a remote folder as a project**: a folder on an SFTP or FTP server is fetched into a folder on this computer and opened as a project, so the Explorer, Go to file and symbol, Search and language servers all work on it. What .gitignore leaves out stays on the server, and files over 4 MB wait there until they're opened. - Each save is sent back at once, beside the old file first; if someone has changed the server's copy since, it asks first. - The server's changes are fetched every two minutes, and with **Project › Fetch the server's changes**; a file open with unsaved changes is never fetched over. - **Project › Sync with the server** shows what's left to decide, by the folder sync's rules: changes made here and not sent, files deleted on one side, and files changed on both sides since the last sync, shown as conflicts to choose a side for. Whatever is replaced or deleted is kept in a backup first. - New files, renames and deletions in the Explorer are done on the server too. - The project remembers its server and folder, and connects again when it's opened.
- **File › Open a remote file (SFTP)** connects to a server, browses its folders and opens a file; **Save to a server** puts any document there.
- A remote file is edited in a copy on this computer, so everything works on it, very large files included; each Save sends it back in the background, to a new file beside the old one first so the server's copy is never half-written.
- If someone else changes the file on the server meanwhile, Save asks before replacing it.
- Sign in with a password or a key file. Passwords can be kept in Windows Credential Manager, never in Limoniter's settings.
- The server's key is shown to be trusted the first time; after that a different key is refused, in case someone is in between.
- **sftp:// addresses** open from the command line, from another program, from a running Limoniter and from the recent files, where remote files are listed by their address; the remote box asks to sign in only if it needs to.
- **Hosts from ~/.ssh/config** are offered in the remote box, with their users, ports and key files.
- **A remote file kept open is watched**: every 15 seconds it's looked at on its server, and a change there is fetched and noticed as a change to any file is, to reload or keep yours.
- **The remote file browser** renames, deletes and makes folders (a right-click on a file or folder, and New folder), and opens several files chosen with Ctrl together.

## Send to device

- **File › Send to device** sends a copy of the file to the machine it's for; the file goes on saving where it always does. **Ctrl+Alt+S** sends it again to the same place under the same name.
- **Serial terminal** (Tools, Hardware): a serial port (an Arduino, a USB adapter on a retro machine's RS-232) at any speed and format, with flow control, DTR reset and break; or a network socket, with telnet when it's wanted, and the Ultimate 64's and Ultimate II+'s modem (port 6400) and telnet menu (port 23) a click away. What comes in is shown as lines of text (ASCII, PETSCII or ATASCII, through Limoniter's character sets, with times if wanted), as a VT100 screen for full-screen menus and BBSes, or as hex both ways with the time to the millisecond. A line typed goes with the ending chosen, or as hex bytes; everything can be logged to a file, as it came or as timestamped hex. **XMODEM, XMODEM-CRC, XMODEM-1K and YMODEM** send the file in front or files chosen (YMODEM a batch, with names and sizes) and receive, with progress, retries and Stop; files received open in a tab or are saved.
- **EPROM programmer** (Tools, Hardware): EPROMs, EEPROMs and flash burned with XGecu's TL866A/CS, TL866II+, T48, T56 and T76 through minipro: the programmer found, the chip chosen from minipro's own list (filtered as you type), the file in front (or the hex editor's bytes) fitted to the chip's size (at the start, at the end or repeated, the rest filled with a byte of your choice) and written, then verified; read into a new tab, blank-checked, erased, or its pins' contact checked, with minipro's words shown as it goes. Where minipro isn't installed, it says how to get it.
- Devices are set up once, by name, in **Manage devices**:
  - A card or stick found by its volume label, whatever drive letter or mount point it has today (a Gotek's stick, an SD2IEC, a MiSTer's or an Amiga's card). It can be ejected once the file is on it.
  - Any folder: a shared network folder, an emulator's folder, or a TNFS server's folder for FujiNet.
  - An SFTP server (a MiSTer, a Raspberry Pi), with the server's key checked as for remote files.
  - An FTP server, such as an Ultimate 64's or an Amiga's.
  - A ZX Spectrum Next over Wi-Fi: Limoniter serves the file, and `.sync` on the Next fetches it (Jari Komppa's NextSync, versions 3 and 4).
  - An Ultimate 64 or 1541 Ultimate, which runs a `.prg` or `.crt`, plays a `.sid` or `.mod`, or puts a disk image in drive A straight away (firmware 3.11 or later).
  - A command line of your own, given the copy's path, such as an emulator.
- The copy can be written in a machine's own character set and line endings (any system preset) without changing the file.
- On a card or in a folder the copy is written under a temporary name, flushed, and then renamed, so a card pulled out straight afterwards never holds half a file. If the copy there has been changed since it was last sent, or a file of that name wasn't sent from here, you're asked first.
- An add-on's `on_send` function runs first, and can see the device (`send_device()`) and change the name the file is sent as (`set_send_name()`).
- Passwords for FTP and the Ultimate are kept, if you ask, in the system's credential store.

## Git

- **Source control** (**Ctrl+Shift+G**, or Tools › Git): the branch, what's changed, what's ready to commit, and anything in conflict. **+** puts a file in the next commit, **−** leaves it out, **↶** throws away its changes; write what the commit does and press **Commit** (with nothing staged, every change to files Git has goes in). **Add to the last commit** folds them into it.
- **Push**, **Pull** (only when it simply follows on, so nothing is merged by surprise) and **Fetch**; when your commits and the ones online have both moved on, **Pull, putting mine after theirs** (a rebase), with **Carry on** and **Abort** if it stops at a conflict, and **Abort the merge** for one partway through, with how far ahead or behind the branch is; switch branches, or make a new one. Git runs in the background, and its own sign-in window, SSH keys and signing work as they do at a command line; Limoniter never holds a Git password.
- Marks beside the line numbers show what's changed since the last commit: green for new lines, blue for changed ones, and a red notch where lines were taken out. They follow your edits as you type.
- **Put the change at the cursor in the next commit**, or **Undo the change at the cursor** (an edit, which Undo takes back).
- **Compare with the last commit**, and a file's **History**: every commit that changed it, to compare with now or open as it was. A comparison opens in a tab, with the file still editable beside the commit. A whole folder can be compared with the last commit too, from the Project panel or Compare folders.
- **Put aside** every change (a stash), to bring back later or throw away; and **Tags**: tag the commit, as a release is named, and push it online.
- **Write it for me**: the assistant writes the commit message from the changes, for you to read over. In a conflict, **Ask the assistant** suggests lines that do what both sides meant, shown first like any suggestion. Both are kept in the Assistant's history.
- **Show who changed each line**: the author, date and commit of the line the cursor's on, in the status bar.
- When a merge stops at a conflict, a bar over the file offers **Keep mine**, **Keep theirs** or **Keep both** for the conflict the cursor's in, goes to the next, and marks the file settled when they're all done.
- **Merge**, in a tab of its own: the original, mine and theirs side by side above, lined up and scrolling together, with each side's changes coloured and conflicts in red, and the merged result below to edit. Lines only one side changed, or both changed alike, are merged already; each conflict waits between markers for **Take mine**, **Take theirs**, **Take both (mine first)**, **Take both (theirs first)**, **Take the original**, or editing by hand. **Next conflict** and **Previous conflict** go round them, the bar counts those left, and saving with any left asks first. Line endings changed on one side don't count as changes, and the result is saved in mine's encoding and line endings.
- **Resolve in merge…** for a file Git stopped a merge in (in Source control, or the bar over the file) opens the merge from Git's own copies of each side, and offers to mark the file resolved (`git add`) once it's saved with nothing left. Any file with conflict markers in it, plain or with the original shown, offers to be resolved in the merge tab too. **Tools › Git › Merge three files…** merges any three.
- **Use Limoniter for Git diff and merge** sets your own Git settings so `git difftool` and `git mergetool` open Limoniter, asking first if another tool is set and showing which; **Stop using Limoniter for Git** puts back exactly what was there. Repository settings are never touched.
- From a command line, `limoniter --diff LEFT RIGHT` compares two files, and `limoniter --merge BASE MINE THEIRS RESULT` opens the merge in a window of its own and ends with exit code 0 only if the result was saved with no conflicts left, as `git mergetool` expects. `limoniter --help` lists them.
- `limoniter --assemble SOURCE OUTPUT [NAME=VALUE...]` assembles 68000 source for the Amiga into a program as F9 does, without a window: each NAME=VALUE replaces that `NAME equ` line in the source, or is added at its top, so one source can be built several ways (How To Code's examples are tested like this).
- **The Git wizard** takes someone who's never used Git from nothing to their first commit, and to their work online if they'd like: getting Git, their name and email, starting a folder's history (with a starting `.gitignore` to suit it and a first commit) or copying a project from GitHub, and connecting it to a new GitHub repository. Each step says what it does and why.
- A folder that looks like a project, but isn't keeping its history, is offered Git once (**Show me how**, **Not now**, **Never for this folder**).
- Git messages that people meet most come with a line on what to do, such as "Pull first, then Push".

- What runs: a BASIC listing, tokenised (a BBC listing goes on a disc that boots it); a program, tape, snapshot or disk image as it is (`.tap`, `.tzx`, `.z80`, `.sna`, `.bas`, `.nex`, `.prg`, `.t64`, `.d64`, `.crt`, `.ssd`, `.dsk`, `.trd`, `.rom`, `.cas` and others); or the file selected in a disk image. Which machine is worked out from the file: a Commodore program by where it loads, a Z80 snapshot by its header, a +3DOS file by which BASIC it holds. Plain text asks which BASIC it is.
- **The built-in ZX Spectrum** (48K and 128K) runs tapes and snapshots in a panel beside the file, with nothing to install: a BASIC program is loaded at once and running. Click its screen to type on it (Ctrl is Symbol Shift, Esc is Break); its sound, the beeper and the 128K's AY chip, comes out of the speakers, with a Mute button; Pause, Restart and switch it off. Z80 snapshots and TZX tapes are converted for it. Under its screen, the **Spectrum's keyboard** with everything printed on and around each key (keywords, Symbol Shift symbols in red, Extended mode words above and below): click Caps Shift or Symbol Shift and then a key to press them together, both shifts for Extended mode, or hold a key down with the mouse for games; buttons for Break, Delete, Edit, Caps Lock, Graphics, Extended, True and Inverse video, and LOAD "". Under **OpticOS**, which takes keywords letter by letter, the keys show only its letters, symbols and keys (EDIT, CAPS LOCK, the cursor keys, DELETE, and Extended mode's `[ ] { } \ | ~`), and the buttons type `LOAD ""` a letter at a time. The **Keyboard** button hides it.
- **Emulators** are a kind of device: ZEsarUX, Fuse and CSpect for the Spectrum and Next, VICE for Commodores, b2 for the BBC Micro, openMSX, Hatari for the Atari ST, and FS-UAE (Linux, Mac and Windows) and WinUAE for the Amiga. **Find emulators** adds the ones installed; any other can be pointed to, with extra options of your own.
- **The Amiga**: an Amiga program, or 68000 source for one, boots straight into it: it's put in a folder that's the Amiga's hard drive (DH0:, which the program can write files back to), with an S/Startup-Sequence that runs it, and the emulator is started with a configuration made for the run. An `.adf` disk goes in the floppy drive instead. Choose the **model** under the emulator in **File › Devices**: an A500 (OCS, Kickstart 1.3), an A500+ (ECS, Kickstart 2.04) or an A1200 (AGA, 68020, Kickstart 3.1). Kickstart isn't Limoniter's to include, so point at your own for each model, or **Find** them where Amiga Forever (its encrypted ROMs too, with its rom.key), FS-UAE and WinUAE keep them, each told by its checksum and the best chosen for each model; with none, the emulator's own AROS, a free stand-in, is used. The choices are kept.
- **And in Copperline**: 68000 source for the Amiga is debugged at the source line through Copperline's own debug adapter, copperline-ctl, in the Debug panel: Limoniter's assembler writes each instruction's source line into the program (as vasm's `-linedebug` does), Copperline warp-boots it, and breakpoints beside the lines stop where they should wherever AmigaDOS loaded it. **Carry on**, **Step over**, **Step in**, **Step out**, **Pause** and — which no other Amiga emulator can do — **Step back** (Shift+F10) and **Run back**, replayed from Copperline's snapshots; the registers, the custom chips and the call stack; a memory window at any address, register or label, with what changed picked out; why it stopped (an address error, an illegal instruction); and **Profile**, which runs on for some frames and shows the routines and source lines the time went on, a click going to each; **Look for warnings**, which shows what Copperline saw the program do that the chips ignore or get wrong (a byte written to a word register, a read-only register written, a register the chipset hasn't, a pointer past chip memory, a blit started over another) and code it wrote after running it, each at the line that did it; and Copperline's own **Frame analyser**, debugger and console opened in its window.
- **The Atari ST in Hatari**: an Atari ST program (`.tos`, `.prg`, `.ttp`), or 68000 source for one, runs straight away, and an `.st` or `.msa` floppy boots. Under Hatari in **File › Devices**, choose the **machine** (ST, Mega ST, STE, Mega STE, TT or Falcon), its **memory** (512 KB to 14 MB, and TT-RAM on a TT or Falcon), its **monitor** (colour, monochrome or TV; VGA on a TT or Falcon), its **speed** (8, 16 or 32 MHz), **cycle-exact** running and **exact prefetch** for demos that count cycles, and **fast boot**; each machine keeps its own. ## Amiga disks that boot with no file system

- **Tools, Amiga, Boot disk with no file system (trackmo)**: a disk of your own, the way demos and games are made, with no AmigaDOS on it. Each **piece** is an assembler source (assembled by Limoniter's 68000 assembler at its ORG, or at the address given) or any other file (graphics, music, packed data), put at a **first sector** of your choosing and loaded to an **address**. One piece is marked to **start**; a piece can be left unloaded, for a program that loads it itself later.
- **The disk's map**: every sector, a column a track, in each piece's colour, with the boot block's two sectors, what's free (with how much), and any clash. Click a free sector to put the selected piece there; a piece added goes at the first free sectors big enough. Pieces on the boot block, past the disk's end, over each other, with no start or two, are all pointed out before anything's written.
- **The boot block**: Limoniter's example reads each piece from its sectors with trackdisk.device, turns the drive's motor off and jumps to the start, with A6 still ExecBase. **Change it** saves the example's source beside the plan and opens it, to make it your own (a fade, a loader that unpacks); Limoniter writes the table of pieces between its two marked lines each time. However it's written, it's assembled, **checked to fit in its 1024 bytes** (a bar shows how many are used, and too big says by how much), given "DOS", and its checksum worked out as Kickstart checks it.
- **Write the disk** as an `.adf` (880K or 1760K), from blank or over an image of your own, keeping what's already in its other sectors; **Run it** boots it on the Amiga emulator in File, Devices. The plan (pieces, sectors, addresses, boot block) is kept in a `.bootdisk` file to build again after any change; pieces open in the editor are taken as they are there, unsaved changes and all.
- How it was checked: the checksum matches real disks' boot blocks (Gloom, a 1988 megademo, Virtual Karting); a disk built from a program at sector 2 and a message at sector 1500 boots on an emulated Amiga (FS-UAE, Kickstart 2.04), and the program sends the message from sector 1500 out of the serial port.

- **A profiler on the built-in Spectrum**: **Profile** counts the T-states spent at every address while the program runs, contention and interrupts included, and shows where they went by routine (each label and what follows it), with its share and how often it was entered, and the busiest source lines; click either to go there. Click Profile again to stop counting, and the figures stay to read.
- **Debugging Spectrum BASIC** on the built-in Spectrum: click beside a listing's line number for a breakpoint, and the program stops as that line starts, with the line marked; **Next statement** runs one statement at a time (a line's statements one by one), **Carry on** runs to the next breakpoint, and **Stop at the next statement** pauses a running program where it is. While it's stopped, its **variables** are listed: numbers, strings, arrays and FOR loops with their limit and step. A program from a tape stops before its first line runs, so a breakpoint there works too. 48K and 128K BASIC.
- **And in VICE**: 6502 source run on VICE is debugged there through its binary monitor: breakpoints, the line stopped at, A, X, Y, SP and the flags, Step, Step over (a JSR) and Carry on.
- **And in ZEsarUX**: Z80 source run on ZEsarUX is debugged there the same way, through its remote protocol: breakpoints beside the lines, the line stopped at marked, the registers, Step, Step over, Carry on and Pause, in a panel beside the source. Next programs too, which the built-in Spectrum can't run. A Spectrum program is loaded from its tape in Limoniter and handed over as a snapshot, so ZEsarUX stops even at its first instruction.

## Add-ons

- An add-on is a Rhai script that adds its own commands to **Tools › Add-ons** and the command box (F1).
- It can run by itself when a file is opened (`on_open`), just before Save writes it (`on_save`), just before Send to device sends it (`on_send`), or just before Run on machine runs it (`on_run`), for example to tidy a file as it's saved.
- It can show its results in panels of its own (`show_panel`, `add_to_panel`).
- Add-ons live in your own add-ons folder and in a shared folder, so a team can keep one set together.
- A new add-on is off until you turn it on, and one whose file changes is turned off again until you look at it; like any script, it has no files, programs or network of its own.

## VS Code extensions

- **Tools › VS Code extensions** installs the parts of VS Code extensions that are written down rather than
  programmed: from a .vsix file, or found on **Open VSX** (the open marketplace VSCodium uses) by name and
  installed with a click (the build for this computer, where an extension has one for each). Each is listed with
  what it gave, and can be turned off and on, or removed.
- **Colour themes** become document and window themes, with their token colours as a syntax colour scheme.
  **TextMate grammars** (.tmLanguage.json or .tmLanguage) colour their languages, with their file endings.
  **Snippets** join the Snippets box for their language. **File icon themes** (Material Icon Theme, vscode-icons)
  draw the Explorer's and tabs' icons. A language's **configuration** gives its comment marks, brackets that close
  themselves and step over, and lines that indent after an opening one and come back out on a closing one.
- A **language server** an extension starts — one it carries, a Node.js server in it, or one it's known to use —
  is offered as Limoniter's own are.
- An extension's own program (JavaScript) isn't run: one that's nothing but its program says so and isn't
  installed; one with a program says which of its commands and settings are left behind.

## Safety

- Unsaved edits are copied to disk as you type, and offered back after a crash, forced close or power cut.
- Autosave (Settings, Files; off to begin with) saves a changed file by itself once it has had unsaved changes for 15 seconds to 10 minutes. It leaves a file for you to save when saving would need a question answered: never saved before, read-only, on a server, changed by another program, too large, or holding characters its encoding can't. The status bar says when it's leaving one, and why.
- **Keep a backup when saving** (also off to begin with) keeps the file as it was beside it, with .bak added, the first time it's saved in a session.
- **File, Recover unsaved edits** offers them again later; damaged copies are detected by checksum.
- Saving never changes bytes you didn't edit.
- Archives, and disk images of kinds Limoniter doesn't write, are only ever read; files inside images open read-only. A change to an image is written whole and read back before it replaces the old file, and can be undone.
- Files can be opened read-only.
- Other programs' changes are noticed when the window comes back into focus, and every two seconds as well if asked (Settings, Files). A changed file with no unsaved edits can be reloaded without asking, staying at its end if the cursor was there, to follow a log as it grows.

## Printing and display

- **Languages** (Settings, Appearance, Language): the whole window in **French, German, Italian or Spanish** as well as English: the menus and the command box, the settings, the buttons and labels, the messages and problems it reports, and the comments in the source it writes (the starters File, New as opens, the players, programs and tables the tools put in your source). Each language is listed by its own name (Deutsch, Español, Français, Italiano), beside a globe, so whichever is chosen, the way back can always be read. The words are in tables, one a language, kept beside the program's source: a test checks that every word the program shows is in each.
- Print with Windows' print dialog, with an optional header and line numbers; hex view can be printed too (up to 16 MB).
- Font choice, larger and smaller text, full screen and always on top.
- **The window's own font and size** (View, Window font and size): the menus, panels, boxes and status bar, apart from the text's.
- **A wider command box**: its width is the one it was left at.
- **Focus follows the mouse** (Settings): the pane under the pointer takes the keyboard without a click.
- **Parameter hints** above the line, or below it (Settings).
- **Window, Layouts**: save which panels are open (and the output, assistant, document map, file tabs and status bar) under a name, such as Writing or Debugging, and switch between them. **Window, Gather windows** brings every box and tool window back onto the screen.
- **Without a mouse, and with a screen reader**: F10 goes to the menus (the arrows and Enter open them), Ctrl+F6 takes the keyboard out of the editor to the rest of the window and Tab goes on from there, and a box that opens has the keyboard at once (Tab through it, Escape closes it). Screen readers are told the line the cursor is on and where it is, or in hex the byte; the file tabs, the command box's list, the image browser's files, the status bar's Read-only, encoding and line-ending items, and buttons that show only a symbol all have names.

## Themes

- Two kinds of theme: a **window theme** for the menus, panels and boxes, and a **document theme** for the text and everything drawn with it, chosen under **View, Theme**.
- Each document gets its own document theme, by rules about its file ending, language, character set, or whether it's in hex or table view; the first rule that fits wins. Out of the box, Commodore, Atari, Spectrum, BBC and teletext, and Amiga text open in their machine's colours. Any document can also be given a theme of its own.
- 18 document themes, from Limoniter's own and Solarized, Nord, Gruvbox, Dracula and Monokai to Commodore 64, Atari 8-bit, ZX Spectrum, Amiga Workbench, teletext, DOS and green and amber screens, each with one of 29 sets of syntax colours. 8 window themes.
- **View, Theme, Themes and rules** makes your own: copy a theme and change any colour, or make a whole theme from three colours; see it on a sample as you go. Themes can be saved to a file and opened, to share them.
- Files opened from Explorer join the open window as tabs, or can each have a window of their own.
